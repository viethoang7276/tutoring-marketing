Course prelaunch and early-bird free access

A reusable launch mode for every course, first used for Financial Accounting - Part 1. Built from a read-only check of the tutoring-web code on development (HEAD a7b36ffb). The CTO owns the final design

Short answerWhat existsOptionsStudent flowAdmin UIData modelEdge casesDecisions

Is it a code? We recommend no code. A student signs up, presses Reserve early-bird access on the course page, and gets free access automatically on launch day. Codes stay available for special cases (partners, a class you teach) but are not the main route

Why: a code in a public post gets copied and shared beyond the people we meant, the app's codes cannot reach $0 today (a €1 minimum and checkout only works on live courses), and codes don't tell us which course a person wants. A reservation does

1 · What the app already has

Most of the plumbing exists

  • Access to a course is one live Enrollment row, and it can already end on a date (expiresAt, enforced). content.prisma:578
  • Enrollments have a source: purchase, gift, adminGrant. Admins can grant one person lifetime access by hand on the user's Courses tab. No bulk grant, no end date. course-access.ts:108
  • Course status is draft | comingSoon | published | archived. There is no launch date and no prelaunch state. content.prisma:5
  • Free preview lessons exist (freePreview, previewLessonId) but only work once a course is published. lesson-access.ts:100
  • The "Notify me" box writes an email-only waitlist. The new waitlist (WL, in the release now going out) stores UTM and links to an account. marketing.prisma:218
  • A new email/password sign-up ignores redirectTo and lands on /start, so "sign up and come back to the course" doesn't work yet (Google sign-in does). sign-up/page.tsx:41
  • Nothing records where a sign-up came from. /api/v1 has waitlist counts, not sign-up or enrollment counts
2 · How a student gets free access

Four ways, one recommended

Recommended

A. Reserve on the course page

Signed-up student presses Reserve. On launch day every reservation becomes a free enrollment

  • No code to share or leak
  • Knows which course each person wants, so it works for every future course
  • Cap and window checked on the server
  • Needs a reservation table and a launch job

Best fit for "sign up and reserve" posts and for repeat launches

Simplest build

B. Automatic at sign-up

Any account created inside the window gets the course, no click

  • One hook in the sign-up code
  • Gives the course to people who never wanted it
  • Doesn't scale to two courses launching at once

OK for a one-off, weak as a common feature

Special cases

C. Redeem code

Student types EARLYFA on the course page

  • Good for partners, a class, one platform's audience
  • Public codes spread to coupon sites
  • Needs a new $0 path: today codes stop at €1 and checkout refuses unlaunched courses

Keep as an extra lever, not the main route

Fallback only

D. Admin grants from the waitlist

At launch you export the waitlist and grant access by hand

  • Works today, no build
  • One person at a time in the admin, slow past ~20
  • No tracking per platform

Use only if the build misses the launch

5 · Database logic

Two new tables, three small changes

Schema work stays in the CTO lane and is done one change at a time. Names are suggestions

// Course: add a prelaunch state and a launch date
enum CourseStatus { draft  comingSoon  prelaunch  published  archived }
model Course { … launchAt DateTime?  ctaLabel String? }

// The offer, one per launch, editable in the Launch panel
model CourseOffer {
  id            String   @id
  courseId      String
  kind          OfferKind  // earlyBirdFree (later: earlyBirdPrice)
  opensAt       DateTime
  closesAt      DateTime
  cap           Int?       // null = no cap
  accessDays    Int?       // null = lifetime
  existingUsers Boolean    @default(true)
  active        Boolean    @default(true)
  reservations  CourseReservation[]
}

// One row per person per course
model CourseReservation {
  id                   String   @id
  offerId              String
  courseId             String
  learnerProfileId     String
  utmSource            String?  // + medium, campaign, content, ref, go-link code
  createdAt            DateTime @default(now())
  convertedEnrollmentId String? @unique
  cancelledAt          DateTime?
  @@unique([courseId, learnerProfileId])
}

// Enrollment: new source so reports can tell early birds from buyers
enum EnrollmentSource { purchase  gift  adminGrant  earlyBird }
model Enrollment { … offerId String? }
  • Reserve runs in one transaction: offer active and inside its window, cap not reached (count with a row lock), email verified, no active enrollment, no existing reservation. Then insert
  • Launch job (Inngest, at launchAt or on "Go live now"): set the course to published, then for each open reservation create an enrollment the same way findOrCreateActiveEnrollment does, with source earlyBird and expiresAt from accessDays. It is safe to run twice, because convertedEnrollmentId marks what is done
  • Access check: one added rule in getLessonAccess, so freePreview lessons also open while the course is prelaunch. Everything else stays locked until launch
  • Counts for marketing: /api/v1/marketing/course-launch-stats with reservations, preview starts and enrollments by day and source. Counts only, no personal data
6 · Edge cases

What can go wrong, and the rule for each

CaseRuleRisk
Two people take the last place at the same momentCap counted inside the reserve transaction with a lock. The loser sees "The early-bird places are gone" and can still join the launch noticeHigh
Window closes while the page is openThe server checks the window on every reserve. The page hides the offer after closesAt on its next loadMedium
Fake or throwaway accounts to grab placesReserve needs a verified email, one per person (unique per learner and course), and existing bot checks and rate limits on sign-upHigh
Email sign-up loses the way back to the courseFix redirectTo for email sign-ups (today only Google honours it). Also carry the offer parameter through email verificationHigh
Person already owns the courseNo reservation. The button reads "You already have this course"Low
Person has an expired or revoked enrollmentAllowed to reserve. At launch the enrollment is reactivated with the offer's terms, matching how purchases work todayLow
Accounts that existed before the windowControlled by the "Who qualifies" setting. Default: they qualify, because they're our warmest peopleMedium
Early bird with limited access (for example 90 days) wants to keep itBuying later uses the normal checkout. findOrCreateActiveEnrollment clears expiresAt, so the purchase becomes lifetime accessLow
Launch date movesAdmin edits launchAt. Reservers get one "new date" email. Reservations stayMedium
Course is cancelledAdmin cancels the offer. Reservations are marked cancelled and reservers get one email. Nothing was paid, so no refundsLow
Launch job fails halfwayRerun is safe: it skips reservations that already have an enrollment. An admin alert fires if any remainMedium
Someone paid €99 just before the offer was announcedPolicy call for Hoang. Suggested: offer them the same free grant or a refund on requestMedium
Refund of a course purchaseToday a refund doesn't revoke course access (the charge.refunded webhook does nothing). Separate bug, worth fixing in the same passMedium
Account deleted (privacy request)Reservation is deleted with the learner profile. Counts in reports stay as anonymous totalsLow
Time zonesAll offer times are stored in UTC and set and shown in Europe/Madrid in the admin. Students see their local timeLow
Two courses in prelaunch at onceOffers and reservations are per course, so each launch runs on its ownLow
